# Единый контракт учебных демонстраций

Статус: specification + исполняемые локальные reference-тесты. Это не подтверждение работы Codex, OpenCode, Pi, bb, Hermes, Full или Ouroboros.
Источник истины для учебного текста: content/course.py. Реальные доказательства допуска находятся только в production/demo-evidence.json и связанных проверенных файлах. Все сцены до допуска являются теоретическим разбором ожидаемого пути. Запрещено представлять mock, reset-снимок или подготовленную сводку как результат агента.

## 1. Сквозной результат

Agent Workshop Inbox обрабатывает только синтетические заявки. Детерминированный код нормализует, классифицирует известные категории и считает итоги. Модель может готовить ограниченный анализ, но не определяет корректность своей проверки. Результат является локальным черновиком; нет адресата, команды отправки, ключей или сетевого side effect.

Три места исполнения различаем: UI, tools, модель. Локальный интерфейс не гарантирует локальную обработку модели. Перед записью подтверждаем допустимость выбранного маршрута и данных. Никаких платных модельных вызовов в этом reference-наборе нет.

## 3. Session-start

Проверяем реальный root, branch/worktree, dirty status, state ID, commit и hash файлов. Читаем требования, решения, последний handoff и единую команду проверки. Неизвестный корень, неизвестный ID или неописанные изменения блокируют работу. Codex и OpenCode используют AGENTS.md и общие docs, а настройки подключения остаются в отдельных адаптерах. Наличие каталогов .codex и .opencode не означает их автоматическую загрузку; trace должен показать чтение реально поддерживаемого входа.

## 4. Session-end и согласованность записи

1. Снимаем полный детерминированный test report с ID, status и reason каждого теста. Отсутствующие тесты, дубли и дополнительные неизвестные результаты являются ошибкой контракта.
2. Сверяем с заранее неизменяемым контрактом этапа. На этапе 02 допускается только известный интеграционный failure с точной причиной classification_missing. Этап принимается, но весь проект не объявляется готовым. На этапе 03 ожидаем прохождение всего набора. Неожиданный PASS ожидаемого failure тоже требует пересмотра состояния, а не молчаливого принятия.
3. Фиксируем изменённые файлы, commit/worktree hash, from/to, done, remaining, verify, expected_failures, risks.
4. Записываем state и handoff в одну неизменяемую запись с уникальным run ID. Временный файл fsync, затем атомарное переименование. Публикуем один атомарный указатель CURRENT на эту запись. Читатели получают state/handoff из одной версии; отдельные Markdown-файлы являются экспортом, не второй истиной.
5. Ошибка теста, сериализации, записи state/handoff или переключения CURRENT не меняет прежнее принятое состояние. Возможная неподключённая запись не является успехом; журнал ошибок хранится отдельно.
6. Повтор того же request/run ID с тем же содержимым возвращает тот же артефакт. Конфликтующий повтор отвергается. Новый run ID создаёт новую запись и не перезаписывает старую. Конкурентное завершение ограничено lock; никакого last-writer-wins без проверки предыдущего состояния.

Reference implementation: implementation/contracts/reference.py. Это проверка поведения контракта в временной локальной директории, а не установленный scripts/session_end.py в реальном demo-проекте.

## 5. Codex → OpenCode: proof-path

Версии/модель/права → reset 01 в отдельном disposable clone → session-start → запрос ограниченного normalizer-этапа → реальные file reads → реальный diff → целевые и интеграционные тесты → session-end этапа 02 → handoff с commit/hash → открываем те же файлы в OpenCode без первого transcript → повтор проверки этапа 02 → классификатор → полный набор → валидная по форме и смыслу сводка.

Reset предназначен для начала дубля и восстановления после сбоя. Внутри удачной передачи reset не заменяет результат Codex. При монтаже стык двух записей должен показывать совпадающие commit/hash. Если это не так, сцена становится подписанным разбором подготовленного состояния, не реальным handoff.

Нужны два полных прогона из исходного состояния. Для каждого: версия, конфигурация без секретов, stdout/stderr/exit status, diff, test report, state/handoff, конечный артефакт, связанное видео или терминальный capture, метки времени, hash. Fallback допустим только из тех же полных проверенных дублей.

## 6. Pi: proof-path

До записи установлен pinned Pi, проверена документация extension API. Команда регистрируется поддерживаемым механизмом. Расширение не меняет core, auth или глобальные settings; проверяет признанный root и branch/worktree; вызывает фиксированный script path массивом аргументов без shell interpolation; показывает progress и exit status.

Показываем limited diff → reload → /session-end success → второй уникальный запуск → error fixture → неверный каталог → удаление extension и повтор базовой проверки. Success содержит ссылку на согласованный handoff; error не меняет CURRENT. Нельзя выдавать теоретическую команду за установленную.

## 7. bb: proof-path

Работа в отдельном worktree bb, не в выдуманном .bb/plugin. Фиксируем commit/install/build и изученный существующий command/action path. Реализация должна быть минимальным обратимым patch существующего UI и handler.

Кнопка Close session имеет idle/running/success/error. Пока running, повторная активация не запускает процесс; backend защищён независимо от disabled UI. Backend проверяет root и fixed argv; ссылка открывает артефакт только внутри проекта. Нужны build/tests, success/error, duplicate, wrong root, проверенный revert и повтор базового запуска. Пока этого нет, показываем архитектуру интеграции без рабочей кнопки.

## 8. Hermes: три независимых границы

Контекст: отдельный demo-профиль, синтетические memory/skill/inbox, без доступа к личной памяти; никакой cron или Telegram send во время automated reference-тестов.

Возможности: документация говорит isolated context и inherited tool access. Требуется реальная техническая allowlist инструментов, путей и сети у родителя и субагента. Описательная инструкция не заменяет запрет ОС/контейнера или инструментального шлюза. Доступ к произвольному пути, symlink escape, произвольной shell-команде, сетевой отправке и личной памяти должен завершаться отказом до side effect. Reference CapabilityPolicy проверяет только свой интерфейс и не доказывает OS sandbox Hermes.

Результат: JSON-схема проверяет форму. Независимо сверяем точный набор ID, уникальность, количество заявок, числа по категориям, critical IDs, исходные факты, допустимое следующее действие и hash входов. Валидный по форме JSON с ложным ID/количеством/выводом отклоняется. После отказа нет успеха и внешней отправки.

Proof: request → разрешённые context/skill → фактические tool reads/delegation → validator → artifact. Два повторяемых запуска, negative access/semantic paths, локальный результат и sanitized capture. Текущие unit tests не являются этим live trace. Если автор отдельно показывает Telegram, действие выполняет автор в разрешённом тестовом канале после ручного допуска; это отдельная внешняя операция, не часть локального gate.

## 9. Ouroboros: независимый evaluator и выключенное применение

Самоизменение означает изменение собственной работы. Оно может быть сделано extension или кодом; оно не означает доказанного улучшения. Проектный README является self-description, не независимым benchmark.

Учебный trace: проблемный вход → bounded proposal → неизменяемый evaluator → независимое ревью → кандидат версии. Evaluator/tests/fixtures/policy лежат за пределами разрешённого patch scope и имеют контрольный hash. Попытка ослабить проверку, traversal, binary patch или изменение evaluator отвергается. Разрешён только явно ограниченный файл изменения; опасный код в нём всё равно требует отдельной проверки, allowlist пути не доказывает безопасность содержимого.

В demo apply отсутствует: rollout.enabled=false, функция применения всегда отказывает. Плохой patch останавливается до применения. Откат кода имеет точную исходную версию, но не может отменить утечку или отправку. Статический разбор называется учебным, если он не произведён pinned Ouroboros.

## 10. Постоянство: события, бюджет, отмена

Идентификатор события резервируем до действия: повтор не исполняется. Права, бюджет и stop проверяются до каждого следующего шага. Журнал сохраняет отказ/начало/результат. Ошибка после возможного внешнего side effect не даёт автоматического retry: сначала ручная сверка, чтобы не повторить отправку.

Reference ControlPlane показывает at-most-once и остановку на локальном callback без сети. Он не заявляет exactly-once во внешнем сервисе и не является daemon/cron deployment.

## 11. Full, частный модельный маршрут, время, шрифт и композиция

- Full: нужен capture именно Full с проектом, пользователями, границей доступа и одним реальным действием. Light не заменяет Full. Пока его нет, схема и «Не подтверждено» остаются безопасным вариантом.
- Частный маршрут Глеба: нужно различить внешний CLI для вспомогательной задачи и замену основной модели. Пока архитектура не подтверждена владельцем, не рисуем её.
- Длительности: прежние числа были планом, не замером. Новые таймкоды допустимы после реальной спокойной записи с паузами и проверкой proof-path монтажёром. WPM-оценка не называется репетицией.
- Igra Sans: файл уже был предоставлен с дизайн-системой и используется локально. Право на дальнейшее распространение подтверждает владелец; это не устанавливается computed-style тестом.
- Камера: 28% ширины × 32% высоты снизу слева. При present=1 и ширине ≥1280 весь значимый сайт находится правее камеры. На 390/768 сайт остаётся режимом чтения; камера допускается только во внешней композиции вне захваченной области. При смене сайта на терминал/продукт монтажёр должен сохранить тот же безопасный layout. Это не проверяется одним screenshot сайта.

## 12. Машинный production gate

Команда: python3 tools/demo_gate.py. Если manifest не содержит полный реальный пакет, возвращает exit 2 и BLOCKED. Она не включает demo автоматически и не разрешает сетевую отправку. Локальная приёмка сайта проверяет правильность закрытого состояния; публикация учебных страниц не означает допуск operational demo к записи.

Для каждого demo требуются два разных run ID, pinned version, реальные журналы, diff, тестовый отчёт, артефакт и capture; все локальные файлы должны существовать и совпасть с sha256. Provenance и негативные сценарии проверяются по связям run ID/test report, а не по произвольному флагу pass. Ручное ревью происхождения и финальный допуск автора остаются обязательными: хэш доказывает неизменность файла, но не правдивость снятого видео.
